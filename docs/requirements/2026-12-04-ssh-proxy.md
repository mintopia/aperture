# SSH REST Proxy

## Introduction

The aim of this is an SSH REST Proxy. So that Aperture can make REST calls to an API and then recieve the result of SSH commands. SSH Connections should remain open for a configurable keepalive time, so that subsequent calls are quick to establish.

## Approach Options

There are two main ways this can work:

1. Generic SSH Proxy - API client specifies the commands to run, output is returned and parsed by the client.
2. Defined Interfaces - SSH Proxy has a list of supported switches/services and commands; eg:

 - Switch
   - Get All Interfaces Statuses (eg. sh int)
   - Get Interface Status (eg. sh int Gi0/1)
   - Get Interface Config (eg. en, <password>, sh run int Gi0/1)
   - Shut Port (eg. en, <password>, conf t, int Gi1/0/1, shut, do wr)
   - Unshut Port (eg. en, <password>, conf t, int, Gi1/0/1, unshut, do wr)
   - Get MAC Address Table for Interface (en, <password>, sh mac address-table int Gi0/1)
   - Get MAC Address Table (en, <password>, sh mac-address-table)
 - Router
   - Get DHCP Leases

The downside to this approach is all the logic is in the SSH proxy. Whereas if approach 1 is taken, it's generic and can be used for other SSH services.

## Known Concerns

From previous attempts to implement this, the following things we identified as needed handling:

### Authentication

We generally need to authenticate as a user with either username/password or username/private key. This could look like:

```
{
    "hostname": "sw-core.event.network",
    "username": "admin",
    "password": "foobar"
}
```json

Or:

```
{
    "hostname": "sw-core.event.network",
    "username": "admin",
    "key": "<RSA Key Here>
}

### Multiple Commands

We generally need multiple commands to achieve what we want to do, eg.

```
en
<password>
sh run int Gi0/1
exit
```

So we need to be able to specify the commands:

{
    "hostname": "sw-core.event.network",
    "username": "admin",
    "password": "foobar",
    "commands": [{
        "command": "en"
    }, {
        "command": "<password>"
    }, {
        "command": "sh run int Gi0/1"
    }]
}

### Inconsistent State

The switch may need to be in a particular state for some commands, eg. enable mode. This might mean we only want to run some commands some of the time. It may also be left in a state after a previous command, eg. enable mode.

We need to be able to set a condition for what to do based on the current prompt/last line of output:

```
sw-lab(config)#
```

We would need to exit out of conf mode. So our request could involve a condition based on the last line:

{
    "hostname": "sw-core.event.network",
    "username": "admin",
    "password": "foobar",
    "commands": [{
        "if": "/^.*\>$/",
        "command": "en"
    }, {
        "if": "Password:",
        "command": "<password>"
    }, {
        "command": "sh run int Gi0/1"
    }]
}

### Expected Output

We need to keep reading multi-line output, so need to read until we either either get a timeout reading with no input, or an expected line is read.

eg:

{
    "hostname": "sw-core.event.network",
    "username": "admin",
    "password": "foobar",
    "commands": [{
        "if": "/^.*\>$/",
        "command": "en",
        "expect": "Password:"
    }, {
        "if": "Password:",
        "command": "<password>",
        "expect": "/^.*\#$/".
    }, {
        "command": "sh run int Gi0/1",
        "expect": "/^.*\#$/".
    }]
}

### Locking

We can only handle 1 request at a time for an individual server, so should not allow requests while 1 is already being processed.

### Status

An endpoint for viewing currently open connections and their connected time would be good.

### Authentication

This is an internal service used internally, a fixed API key would be sufficient.
